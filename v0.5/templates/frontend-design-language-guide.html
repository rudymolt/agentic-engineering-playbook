Frontend design language

Durable design guidance

Build screens as dense workspaces, not card galleries.

This guide documents the interaction language that sits above the kitchen sink: full-width operational items, right-side drawers for routine changes, and an in-place history disclosure for longer edit history. The app is desktop-first (body min-width 1200px); responsive behaviour in this guide is for the document only.

Foundation

Application-Level Principles

Use these when turning a product idea into a screen before choosing individual controls.

1 Items are full width by default.

Roster members, timetable entries, transport movements, room assignments, and review items should read as horizontal rows or table rows. Reserve cards for repeated summary blocks or modal content.

2 Routine changes happen in a drawer.

Add, edit, review, assign, restore, and route changes should open a right-side drawer. The source list stays visible as context while the operator completes the change.

3 History is short inline, long behind a disclosure.

Show the latest event near the object it belongs to. A Show more action expands the vertical timeline in place (capped height, internal scroll). Modals are reserved for destructive confirmations, not for reading history.

4 State should be visible before action.

Use filter chips, status badges, legends, and row selection before opening an editor. Never make the drawer carry information the row needed for scanning.

Pattern notes

Why this shape works

  • Full-width rows carry scan data. Name, role, status, and the next action stay on one horizontal read line.
  • The drawer handles change. The row does not expand into a form. It opens a focused editing surface.
  • Inline history stays tiny. Only the latest event appears here. Older events expand in place behind the Show more disclosure.

Change pattern

Drawer Changes

The drawer is the default surface for changing one selected object. It should have a sticky header, clear save/cancel actions, and enough context to avoid jumping away from the current workspace.

Use drawers for

Add/edit forms, assignment details, import review decisions, restore flows, selected row details, and workflow-specific secondary data.

Avoid drawers for

Destructive confirmations with no form, broad page navigation, large comparisons, or history reading beyond the selected object.

Inline

Use for the newest event and immediate undo/recovery when the operator is still working on the same object.

Disclosure expand

Show more expands the timeline in place with a capped, scrollable height. Disabled actions keep their explanation as the button label (for example "Newer change exists").

Dedicated page

Use only when history needs sorting, filtering, export, or cross-object investigation.

Reference

Surface Decision Rules

When a new screen is being designed, choose the surface by operator task rather than by visual novelty.

Operator need Default surface Required behaviour Avoid
Scan or select many records Full-width rows or table rows Visible status, row hover, filter chips, stable columns, internal horizontal scroll for wide tables. Independent cards that make comparison slower.
Add or edit one record Right-side drawer Sticky header, save/cancel footer, selected-object title, validation inline with fields. Expanding row forms that push the list around.
Review a proposed change Drawer attached to the review item Show before/after values, provenance, accept/reject actions, and any conflict state. Modal-only review flows with no source row context.
Read recent edit history Inline latest event plus Show more disclosure Latest event visible; Show more expands in place with capped height and internal scroll; disabled actions explain why. History modals, or long accordions that stretch the workspace.
Confirm destructive action Small confirm-dialog modal (480px) Explicit confirmation check before submission, visible consequence copy, cancel path, danger-styled action. Destructive action hidden inside a toast or hover-only control.
Compare operational state Table/list with legend Colour paired with words, status legend where colour carries meaning, no colour-only decisions. Unlabelled colour strips or decorative status-only icons.

Drawer anatomy rule

Sticky header names the selected object (family name uppercase). Body contains the edit task. Footer owns save/cancel. Drawer state is URL-driven (for example ?edit=<id>) so an open drawer is shareable and survives reload.
