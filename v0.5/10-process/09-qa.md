# 09 · QA — browser-driven end-to-end testing

> Unit tests verify what you thought the code would do; QA verifies what it actually does in a real browser. Run after every slice that touches the UI or has external dependencies.

**This stage in one breath:** Verify the slice end-to-end in a real browser, not just in unit tests. Output: a QA pass, or defects with reproduction steps.

---

## When to run

- After stage 07 produces a green slice.
- Before stage 10 (ship).
- Any time the verification ladder (see `00-foundations.md` §4) calls for end-to-end verification.

Skip for pure backend changes verified by integration tests, unless those tests are themselves new and unproven.

Stage 09 continues the feature's selected Verify route and active run pace from stage 08. It receives the acceptance criteria and review evidence, not builder chat. If QA must launch a new checker, revalidate the same model/runner identity, fast-mode capability when `pace: fast`, and fresh-context boundary through [`../93-model-routing-track.md`](../93-model-routing-track.md); do not silently choose a replacement. Fast pace never shortens the browser matrix or other QA gates and clears when the run hands control back.

## Which route

For new choices, resolve the saved binding at this stage-owned invocation point.
Resume with the retained `approved_binding`, not current defaults; older active
routes without a binding remain unchanged:

```sh
printf '%s' '{"job":"application_qa","owner":"09"}' | python3 {playbook-path}/v0.5/scripts/configure-playbook.py --project . job-route
```

A configured manual binding follows this stage directly. A configured project
route invokes its returned project-relative `SKILL.md` through the existing
selected Launch/Doctor/Drive/Evidence/Cleanup route below. It must already hold
the independent exact-source eligibility proof in the
[job contract](../scripts/skill-bindings.md); configuration creates neither
proof nor harness nor maintenance opt-in. `configured: false` retains existing
routes. Blocked means stop and explicitly edit/preview a manual fallback.
Human permissions, fresh QA evidence, owned lifecycle/cleanup, defect handling
and ship decisions remain authoritative; Doctor is not a behavior pass.

For a custom-retained-audit route, immediately before invoking call
`catalog.invocation_source(saved, "application_qa", "09", route["source_id"])`
on this stage's local catalog, then load the returned private `SKILL.md` through
the host's skill reader in retained report-only mode. Use the same saved
selection or authenticated retained QA execution and external store as
`job-route`; follow the
[custom invocation recipe](../scripts/skill-bindings.md#stage-owned-custom-invocation).
The resolver rechecks that this is the exact already selected project QA route;
it cannot select or create a harness. A portable identity is not a path and
resolution failure blocks. Project-authored summaries and local audit JSON are
not proof of real independent execution; this stage retains that evidence gate.

Report-only verification is the default. Follow this stage manually with the available real
browser/device, or use a direct upstream `/qa-only` only after the resolved installed source
passes `../scripts/check-upstream-compatibility.py`. An unknown, incompatible, or drifted
source takes the manifest's manual stage-09 fallback without invocation.

When a project explicitly adopted `/ai-playbook-verification-harness`, follow its
selected Launch/Doctor/Drive/Evidence/Cleanup route and retain its evidence. A
doctor pass establishes readiness only; QA still verifies the declared behavior.
When the adopted map needs a complete maintenance sweep, use
`/ai-playbook-maintain-verification-harness`: it reports coverage first and
separates any authorized owned-path correction from fresh verification. Only the
owning stage may then record an accepted complete **clean** or **changed** audit
for an explicitly opted-in selected harness; blocked, partial, failed, and
source-only work never resets its clock. The owning stage uses the explicit
selection transition in the maintenance skill when adopting or changing a
harness; status recomputation does not infer or rewrite that transition. It
adds no background watcher or automatic PR.

An explicitly requested `/qa` auto-fix run is a generator, not this verifier. It may create
regression tests under its own top-level workflow contract, but every accepted defect here
normally becomes a separate generator task under stage 07, follows the project commit
strategy, and returns to a fresh stage-09 pass.

## Cross-app flows (V0.2.8)

When the feature spans sibling apps, QA scope includes the cross-app flow end-to-end — the contract tests from stage 07 prove the seam's shape; QA proves the journey through it. Pure backend cross-app changes follow the same skip rule as above: integration/contract tests carry them unless those tests are new and unproven.

## UI smoke matrix

For any UI-touching slice, QA must exercise the affected screens at desktop, tablet, and mobile widths. Record whether the page has horizontal body overflow, whether tables remain readable through internal scrolling, whether mobile interactive targets meet 44px or have a documented compact exception, and whether heading order matches the visible hierarchy.

For URL-driven UI, QA must also test the branch-owned drawer, filter, tab, link, hash, query,
and row expansions. Verify scroll position and focus are preserved where the operator expects
to stay in context, and confirm live filter updates that should remain in place do not use
native form submission.

## For authenticated sessions

`/setup-browser-cookies` first if QA needs to test an authenticated flow. Run this once per project and re-run when the auth changes.

## What QA produces

- Bug reports inline in the conversation.
- Browser screenshots / DOM dumps for any UI bug.
- A pass, blocked, or pass-with-accepted-risk verdict tied to the exercised acceptance criteria.

For a UI pass, retain locatable evidence identifying the tested
revision/environment, exercised journey and matrix cell, action or trigger, and
stable result. Use a screenshot, DOM/accessibility snapshot, or recording as
appropriate; video is optional. Record observable side effects and a reload
round trip whenever persistence is expected. One artifact may support multiple
criteria or cells only when the report says exactly which ones it covers and it
actually demonstrates them. Preserve the evidence through cleanup and redact
credentials or sensitive test data. A missing required artifact is missing
evidence, not an unqualified pass; backend and CLI surfaces retain their
runtime-appropriate evidence and skip rules.

An agent-owned mission persists the QA ledger as a candidate-bound receipt.
Every acceptance criterion, journey, environment, artifact locator, finding,
closure, and accepted human taste/safety decision must resolve before handback.
Cloud evidence stays scoped to the current readiness run; retained sibling
runs cannot substitute for missing current evidence.

When QA pauses or moves to another worker/host, use the conditional
[pickup brief](pickup-brief.md) to name the candidate, environment, artifact
locators, and incomplete gates. A Mac-only or otherwise inaccessible artifact is
an explicit limitation until its permitted input is transferred; it is not a QA
pass.

QA evidence follows the verifier definition in `08-review.md`: act in the browser or equivalent runtime, attach real output or artefacts, and do not let an auto-fix certify itself.

QA findings use stage 07's same bounded remediation and failure-signature accounting during `build all`. A concrete, reversible, in-scope defect may become a separate generator task followed by fresh QA; ambiguity, human-owned decisions, scope growth, three identical failures, or no progress pauses the run. For unrelated suite failures, use stage 08's isolated merge-base classification before calling them pre-existing.
